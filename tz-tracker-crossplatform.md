# Тайм-трекер: кросс-платформенное ТЗ (v2)

Если что-то неясно, выбери самый простой вариант, запиши решение в DECISIONS.md и иди дальше. Не меняй стек и архитектуру без записи в DECISIONS.md.
(Уточнение: «самый простой вариант» означает минимальную реализацию, которая удовлетворяет текущему этапу и не создаёт долга, требующего переписывания на следующем этапе. Если два простых варианта равнозначны — выбирай тот, что требует меньше зависимостей и меньше кода. Запись в DECISIONS.md делай в формате: дата, этап, вопрос, варианты, выбранный вариант, причина.)

## 0. Правила работы (важно)

Платформа разработки
- Не предполагай конкретную ОС: проект должен клонироваться, собираться и запускаться на macOS, Windows и Linux. Все команды — через npm-скрипты; в коде, скриптах и CI не используй пути и утилиты, специфичные для одной ОС (кроме случаев, когда это явно часть сборки под конкретную платформу).
- Работай внутри каталога проекта. Не используй sudo и не требуй прав администратора: если команда требует повышения прав — это сигнал, что она выходит за рамки проекта, остановись и спроси. Исключения: стандартные кэши пакетных менеджеров (npm и т.п.) и каталог данных приложения в рантайме.
- Данные приложения во время разработки лежат в каталоге проекта; в собранном приложении — в системном каталоге данных пользователя (в Electron: `app.getPath('userData')`).

Секреты
- В репозитории не должно быть ключей, токенов и .env. `.gitignore` создай на первом шаге (.env*, node_modules, dist, release, out, .vite, coverage, *.log, *.tsbuildinfo, .DS_Store, Thumbs.db).
  (Уточнение: перед каждым коммитом проверяй `git status --ignored` и `git diff --cached`, чтобы случайно не добавить секрет. Если секрет всё же попал в историю — не «прячь» его новым коммитом, а остановись и сообщи.)
- Не печатай в логи и не коммить переменные окружения.
  (Уточнение: это касается и дампов process.env, и вывода конфигов, и сообщений об ошибках, в которые может попасть значение переменной. Если для отладки нужно знать, задана ли переменная, — печатай только факт наличия, не значение.)

Зависимости (supply chain)
- Минимум зависимостей. Перед добавлением нового пакета напиши в DECISIONS.md, зачем он нужен.
  (Уточнение: в записи укажи альтернативу «своими руками» и почему она хуже. Если пакет нужен только для одной функции — оцени, не проще ли написать её самостоятельно.)
- Не ставь пакеты с неизвестными авторами, с подозрительно похожими названиями и пакеты без активной поддержки.
  (Уточнение: проверяй репозиторий, дату последнего релиза, число мейнтейнеров, наличие provenance/подписи, историю уязвимостей. Пакет без релизов больше года — повод искать альтернативу.)
- Версии фиксируй, package-lock.json коммить, ставь через `npm ci`.
  (Уточнение: фиксируй точные версии в package.json (без ^ и ~) для прямых зависимостей; lock-файл — единственный источник для транзитивных. Обновление версий — отдельным коммитом с записью в DECISIONS.md.)
- Не выполняй `curl ... | sh` и скрипты из интернета. Установочные скрипты зависимостей (postinstall) допускай только для известных пакетов (electron, esbuild).
  (Уточнение: если новый пакет тянет postinstall — это отдельный повод для записи в DECISIONS.md. Проверить наличие скриптов можно через `npm view <pkg> scripts` до установки.)
- Перед финалом выполни `npm audit` и опиши результат.
  (Уточнение: опиши не только итоговую сводку, но и что сделано с найденными проблемами: обновлено, заменено, принято с обоснованием. Если audit недоступен (нет сети) — зафиксируй это в отчёте.)

Процесс
- Работай по этапам из раздела 8. После каждого этапа: сборка проходит, тесты проходят, коммит с понятным сообщением.
  (Уточнение: «понятное сообщение» — префикс этапа, например `M2: drag & resize entries`, и одна-две строки о том, что именно сделано. Не смешивай в одном коммите разные этапы и не коммить сломанную сборку.)
- Не переписывай уже принятые этапы без причины.
  (Уточнение: причина — баг, блокирующий следующий этап, или требование безопасности. В этом случае сначала запись в DECISIONS.md, потом изменение.)
- Если команда может удалить данные или затронуть что-то вне проекта, остановись и спроси.
  (Уточнение: примеры — `rm -rf` вне каталога проекта, `git clean -fdx` без предварительного `git status`, перезапись файла БД без бэкапа, миграции, меняющие формат на диске. Сомневаешься — считай, что команда опасна.)

## 1. Цель

Кросс-платформенное десктопное приложение (Windows 10+, macOS 12+, основной Linux): недельный календарь, в котором время трекается блоками (событиями). Можно запустить таймер, и он создаст блок, или создать блок руками перетаскиванием. Блоки привязаны к проектам. Работает офлайн, без аккаунтов и без сети.
(Уточнение: «работает офлайн» означает, что приложение полностью функционально без интернета после установки. Отсутствие сети не должно влиять ни на одну функцию, включая первый запуск. «Без аккаунтов» — нет регистрации, входа, идентификации пользователя. «Без сети» — в рантайме не должно быть ни одного исходящего запроса; это проверяется в приёмке.)
(Дополнение: приложение также позволяет планировать мероприятия на будущие недели и месяцы — то есть создавать блоки в будущем, а не только фиксировать прошедшее время, — и содержит систему напоминаний о запланированных мероприятиях. Планирование и трекинг используют одну и ту же модель Entry; различие — в статусе блока: прошедший (время уже потрачено), текущий и запланированный (в будущем). Напоминания работают офлайн, без сети и без аккаунтов, пока приложение запущено.)
(Дополнение про мобилу: сборка под iOS/Android в этом ТЗ не делается, но архитектура должна допускать её добавление без переписывания UI и доменной логики — см. раздел 5. Мобильная версия остаётся «вне рамок» по сборке, но не по архитектуре.)

## 2. Стек

Electron + Vite + React + TypeScript (strict).
(Уточнение: strict — это `"strict": true` плюс, желательно, `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes`. Если последние два создают лишнюю боль — запиши решение в DECISIONS.md. UI и домен (renderer/shared) не должны импортировать Electron напрямую — только через слой платформы, см. раздел 5.)
Календарь: FullCalendar (@fullcalendar/react, daygrid, timegrid, interaction).
(Уточнение: используй только эти плагины; не тяни дополнительные (list, timeline, rrule) без записи в DECISIONS.md. Стили FullCalendar подключай локально, не через CDN. FullCalendar и весь UI должны работать и в обычном браузере (dev-режим через browser-адаптер), не только внутри Electron.)
Хранение: один JSON-файл в системном каталоге данных приложения (в Electron: `app.getPath('userData')`), запись атомарная (во временный файл, затем rename), с бэкапом предыдущей версии. Версия схемы в файле для будущих миграций.
(Уточнение: «атомарная» — запись во временный файл в той же директории (чтобы rename был в пределах одной ФС), fsync временного файла, затем rename поверх основного, затем (по возможности) fsync директории. Бэкап — копия предыдущего валидного файла рядом (например, db.backup.json), перезаписывается только после успешной записи новой версии. Временный файл при старте удаляется, если остался от аварийного завершения. Механизм хранения — за интерфейсом, чтобы на мобиле его можно было заменить файловым API shell-обёртки.)
Тесты: Vitest для слоя данных и расчётов.
(Уточнение: тестами покрываются чистые функции из src/shared: расчёт сумм, валидация, миграции, сериализация/десериализация, обработка повреждённого файла, расчёт ближайшего напоминания.)
Сборка приложения: electron-builder, упаковщик под каждую ОС родной для неё (win → zip, mac → dmg/zip, linux → AppImage), сборка каждой платформы на соответствующем раннере CI.
(Уточнение: основной артефакт — zip; остальные форматы — по ходу. Никаких костылей вроде Wine: каждая ОС пакуется на своей платформе в CI, см. раздел 7. Локально обязательны только dev и тесты, полная сборка — задача CI.)
Не добавлять: бэкенд, облако, аналитику, автообновление, нативные модули.
(Уточнение: «нативные модули» — всё, что требует node-gyp/пересборки под Electron. Если зависимость тянет нативный модуль транзитивно — это блокер, ищи альтернативу. Это ограничение — ещё и страховка для будущей мобилы: всё приложение должно оставаться переносимым web-кодом плюс тонкий слой платформы.)

## 3. Модель данных

```ts
type Project = { id: string; name: string; color: string; archived: boolean };
type Entry = {
  id: string;
  projectId: string | null;
  title: string;
  start: string; // ISO 8601, UTC
  end: string;   // ISO 8601, UTC, end > start
  note?: string;
  planned?: boolean;          // true — запланированное мероприятие (по умолчанию false)
  reminder?: number | null;   // за сколько минут напомнить; null/undefined — без напоминания
  reminderFiredAt?: string | null; // ISO 8601 UTC, когда напоминание уже показано (идемпотентность)
};
type RunningTimer = { projectId: string | null; title: string; startedAt: string } | null;
type DB = {
  schemaVersion: 1 | 2;
  projects: Project[];
  entries: Entry[];
  timer: RunningTimer;
  settings: {
    weekStartsOn: 0 | 1;
    notificationsEnabled: boolean;      // глобальный выключатель напоминаний
    defaultReminder?: number | null;    // напоминание по умолчанию для новых блоков
  };
};
```

Правила: время хранится в UTC, показывается в локальной зоне. Пересечение блоков разрешено. Удаление проекта: блоки остаются с `projectId: null`, либо проект архивируется (выбери архивацию). Модель данных одинакова на всех платформах и не знает, где она лежит.
(Уточнения к модели:
- id — строка; генерируй через crypto.randomUUID() (доступен в Electron и Node). Не используй инкрементные счётчики и не полагайся на порядок массива.
- color — строка в формате #RRGGBB; валидируй регуляркой и в renderer, и в main.
- name/title — непустые после trim; разумный предел длины (например, 200 символов) — валидируй на границе платформы, чтобы UI не мог прислать гигантскую строку.
- note — опционально, предел длины (например, 5000 символов).
- start/end — строки ISO 8601 в UTC (суффикс Z); при парсинге проверяй, что дата валидна и end > start. Храни именно UTC-строки, не Date.
- archived: true — проект скрыт из выпадающих списков создания/редактирования, но остаётся в отчётах по уже существующим блокам. Удаление проекта не удаляет блоки.
- settings.weekStartsOn — 0 (воскресенье) или 1 (понедельник); влияет на вид «неделя» и «месяц».
- schemaVersion — целое; при чтении файла с другой версией запускай миграцию (или, если версия новее известной, не перезаписывай файл и покажи понятную ошибку).
- Валидация БД при загрузке: если структура не соответствует типам — считай файл повреждённым (см. M1).)
(Уточнения к полям планирования:
- planned: true — блок в будущем, время ещё не потрачено. При наступлении start блок не меняет статус автоматически; он просто становится «текущим/прошедшим» по сравнению с Date.now(). Отчёт по умолчанию считает только блоки, у которых end <= now (то есть фактически прошедшее время); запланированные в сумму не входят, но могут отображаться отдельной колонкой — реши и запиши в DECISIONS.md.
- reminder — смещение в минутах; допустимые значения: 0, 5, 10, 15, 30, 60, 120, 1440 (и null). Валидируй по белому списку на границе платформы.
- reminderFiredAt выставляется после фактического показа уведомления; повторно то же напоминание не показывается. При переносе блока (start изменился) — сбрасывай reminderFiredAt в null, чтобы напоминание сработало по новому времени.
- Пересечение запланированных блоков разрешено, как и раньше.
- Добавление новых полей не ломает schemaVersion: 1 — если поле отсутствует, считай значение по умолчанию. При изменении структуры повысь schemaVersion до 2 и опиши миграцию.)

## 4. Функции

Календарь: виды «неделя» (основной), «день», «месяц». Сетка по времени для недели и дня.
(Уточнение: «основной» — открывается по умолчанию. Переключение вида — в шапке. Текущая дата/период сохраняются в состоянии сессии; сохранять ли их между перезапусками — реши и запиши в DECISIONS.md.)
Создание блока: выделение диапазона мышью, затем диалог (название, проект, заметка).
(Уточнение: минимальная длительность выделения — например, 15 минут (шаг сетки); выделение короче — округляй до шага. В диалоге проект можно не выбирать (projectId: null). Отмена диалога не создаёт блок. Создание должно работать и с клавиатуры/тачем, не только мышью — UI не должен предполагать наличие мыши.)
Редактирование: перетаскивание, изменение длины, диалог по клику, удаление.
(Уточнение: удаление — из диалога и/или контекстного меню; подтверждение удаления — на твоё усмотрение, запиши в DECISIONS.md. Перетаскивание и ресайз должны сохраняться сразу (или по blur) — выбери и зафиксируй.)
Таймер: кнопка Start/Stop в шапке, выбор проекта и названия. Запущенный таймер показывается на сегодняшнем дне как растущий блок и переживает перезапуск приложения. Stop создаёт Entry.
(Уточнение: «растущий блок» обновляется раз в секунду (или раз в N секунд — зафиксируй). При Stop создаётся Entry с start = startedAt, end = момент Stop; title/projectId берутся из таймера. Если приложение было закрыто дольше, чем шёл таймер, — блок всё равно один, от startedAt до Stop. Таймер хранится как таймстарт startedAt, поэтому переживает любое завершение процесса на любой ОС. Одновременно может быть только один таймер; повторный Start при активном таймере — игнорируется или заменяет (реши и запиши).)
Проекты: список, создание, переименование, цвет, архивация.
(Уточнение: архивированные проекты показываются в отдельной секции или скрываются — реши и запиши. Переименование и смена цвета не меняют историю блоков. Удаления проекта нет — только архивация.)
Отчёт: за выбранный период суммарное время по проектам (таблица) и экспорт в CSV.
(Уточнение: период — произвольные даты начала/конца (включительно); по умолчанию — текущая неделя. Блоки, пересекающие границу периода, учитываются по пересечению с периодом (обрезаются), а не целиком — зафиксируй это в DECISIONS.md, если выберешь иначе. Блоки с projectId: null — отдельная строка «Без проекта». Запланированные блоки в сумму по умолчанию не входят — см. правила в разделе 3.)
Планирование на будущее. В видах «неделя», «день» и «месяц» можно переключаться на любую будущую неделю/месяц (кнопки «назад/вперёд/сегодня» и выбор даты). Создание блока в будущем периоде создаёт Entry с planned: true. Запланированные блоки визуально отличаются (например, пунктирная рамка или приглушённый цвет) — конкретный стиль зафиксируй в DECISIONS.md.
(Уточнение: ограничения по горизонту планирования нет; но если пользователь уходит далеко вперёд, не предзагружай и не рендери всё сразу — FullCalendar делает это сам, не мешай. Минимальная длительность и шаг сетки — как в пункте «Создание блока».)
Напоминания о мероприятиях. В диалоге создания/редактирования блока — выбор «напомнить за …» (никогда / в момент начала / 5 / 10 / 15 / 30 / 60 / 120 минут / 1 день). Напоминание показывается системным уведомлением ОС (на десктопе — Electron Notification, через сервис уведомлений, см. раздел 5) с названием блока и временем начала; по клику — окно разворачивается и открывается соответствующий день/блок.
(Уточнение: на десктопе напоминания работают только пока приложение запущено (в том числе свёрнуто в трей) — фонового демона и автозапуска в рамках этого ТЗ нет, зафиксируй это в KNOWN_ISSUES.md. Планировщик живёт в слое платформы (на десктопе — в main): таймер на ближайшее невыполненное напоминание, пересчёт при изменении БД и при смене системного времени. При пропуске (приложение было закрыто) — при старте не показывай «просроченные» напоминания старше N минут (например, 60), но пометь их как reminderFiredAt, чтобы не копились; решение и N зафиксируй в DECISIONS.md. Дубликаты исключай через reminderFiredAt. Глобальный выключатель — settings.notificationsEnabled; при выключенном напоминания не планируются и не показываются, но настройки блоков сохраняются.)
Управление напоминаниями. В диалоге блока можно снять напоминание; при удалении блока его напоминание снимается автоматически. Если у блока изменилось время начала — напоминание пересчитывается (см. сброс reminderFiredAt).
(Уточнение: отдельного экрана «все напоминания» не требуется. В шапке достаточно индикатора, что напоминания включены/выключены, — опционально.)
Трей (только десктоп): приложение сворачивается в трей, пункты меню «Открыть», «Старт/Стоп таймера», «Выход».
(Уточнение: закрытие окна крестиком сворачивает в трей, а не завершает приложение (см. M3). «Выход» — полное завершение. Иконка трея должна быть локальной; при отсутствии иконки — используй простую заглушку, но не тяни её из сети. Трея нет на будущей мобиле, поэтому вся логика трея — только в десктопном слое платформы, не в UI.)
Горячие клавиши (только десктоп): Ctrl+N (Cmd+N на macOS) новый блок, Space Start/Stop (когда не в поле ввода), Ctrl+E (Cmd+E) экспорт.
(Уточнение: используй accelerator CommandOrControl, чтобы на macOS работала Cmd. «Не в поле ввода» — фокус не в input/textarea/contenteditable. Space не должен скроллить страницу, когда обрабатывается как горячая клавиша. Ctrl/Cmd+N не должен открывать новое окно Electron — перехватывай и предотвращай поведение по умолчанию. Горячие клавиши — необязательный бонус, а не основной путь: все действия доступны через UI.)
Тёмная и светлая тема по настройке системы.
(Уточнение: на десктопе реагируй на смену темы системы в рантайме (nativeTheme), без перезапуска. Реализация — CSS-переменные и prefers-color-scheme в renderer, чтобы та же тема работала в любой web-обёртке в будущем. Ручного переключателя темы не требуется.)

## 5. Архитектура

Ключевое требование: UI и доменная логика не знают, на какой платформе они запущены. Всё платформенное — за интерфейсом PlatformApi, чтобы позже добавить мобильную оболёртку (Capacitor или аналог) без изменений в UI и shared.

src/shared: типы и чистые функции (расчёт сумм, валидация, миграции). Не импортирует Electron и платформенные модули. Покрыть тестами.
(Уточнение: именно shared используют и слой платформы, и UI, и тесты. Для напоминаний — чистые функции: nextReminderAt(entries, now), isPlanned(entry, now), validateReminderOffset, resetReminderOnTimeChange(oldEntry, newEntry). Покрыть тестами, включая граничные случаи: напоминание в прошлом, смена времени, выключенные уведомления, блок без напоминания. id лучше передавать снаружи, чтобы функции оставались чистыми.)
src/renderer: React UI, состояние в одном store (например, Zustand или reducer). Доступ к платформе — только через интерфейс PlatformApi (loadDb, saveDb, exportCsv, timerStart/Stop, remindersSetEnabled, onReminderActivated и т.п. — явный типизированный список) и flags возможностей (hasTray, hasHotkeys). Ничего не знает про Electron.
(Уточнение: «один store» — единый источник истины для projects/entries/timer/settings; производные значения (суммы, отфильтрованные списки) вычисляются селекторами, а не хранятся. В renderer запрещены импорты 'electron' и node-модулей — это проверяется (см. приёмку). В store — селекторы «запланированные на период», «ближайшие напоминания» (для индикатора, опционально).)
src/platform/electron: main — окно, трей, работа с файлом данных, IPC-обработчики, планировщик напоминаний, показ уведомлений; preload — через contextBridge экспортирует узкую реализацию PlatformApi (никаких ipcRenderer и require в renderer).
(Уточнение: main — единственное место, где есть доступ к fs и к app.getPath. Вся валидация данных, приходящих из renderer, — здесь. Планировщик напоминаний (reminders.ts): расчёт ближайшего напоминания по entries, установка setTimeout (с пересчётом, чтобы не полагаться на длинные таймауты), показ Notification, запись reminderFiredAt через тот же атомарный механизм сохранения БД. Уведомления показывает только main; renderer инициирует их через API, но не напрямую.)
src/platform/browser: реализация PlatformApi для запуска renderer в обычном браузере (dev-режим): хранилище в localStorage/памяти, экспорт через download-ссылку, уведомления через Web Notification API где возможно, без трея и горячих клавиш.
(Уточнение: это не фича пользователя, а архитектурный тест: если UI можно запустить в браузере — значит, он действительно отделён от Electron и готов к мобильной оболёртке. На мобиле позже появится src/platform/capacitor с той же сигнатурой PlatformApi (файловая система, локальные уведомления) — UI и shared не изменятся.)
Сервис уведомлений — часть PlatformApi, а не прямые вызовы в UI: сейчас Electron Notification, позже — нативные локальные уведомления мобилы.
(Уточнение: клик по уведомлению не должен открывать произвольные URL; максимум — сфокусировать окно и перейти к дате блока внутри приложения.)

## 6. Требования безопасности к приложению

contextIsolation: true, nodeIntegration: false, sandbox: true (проверь явно в webPreferences, не полагайся на дефолты версии Electron).
Строгий CSP в index.html (только 'self', без unsafe-eval).
(Уточнение: пример директивы: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'. 'unsafe-inline' для стилей допустим только если требуется выбранным способом стилизации; если можно без него — убери. CSP должен работать и в dev (включая browser-режим), и в prod.)
Никакой загрузки удалённого контента, никаких CDN: все ресурсы локально.
(Уточнение: шрифты, иконки, стили — из node_modules или локальных файлов. Проверь, что в собранном бандле нет абсолютных http(s)-URL на ресурсы.)
Блокировать навигацию и window.open; внешние ссылки открывать только для https: через shell.openExternal с проверкой URL (в этом приложении их, скорее всего, не будет).
(Уточнение: обрабатывай will-navigate, setWindowOpenHandler, will-attach-webview; для внешних ссылок проверяй протокол строго https: (не http:, не file:), и только после этого shell.openExternal.)
Все данные из renderer на границе платформы валидировать в main (тип, длины, формат дат).
(Уточнение: валидация — на входе каждого IPC-обработчика, до любой записи на диск. Невалидные данные → ошибка в renderer, файл не трогается. Не доверяй типам TypeScript на границе IPC — проверяй в рантайме.)
Не использовать eval, new Function, dangerouslySetInnerHTML.
(Уточнение: также не используй innerHTML с динамическим содержимым и сторонние библиотеки, которые это делают под капотом. Если библиотека необходима — запиши в DECISIONS.md и проверь её поведение.)
DevTools в production-сборке отключены.
(Уточнение: не открывай DevTools по хоткею в prod; webContents.openDevTools — только в dev-режиме.)
Путь для экспорта CSV выбирается через системный диалог сохранения (dialog.showSaveDialog в main).
(Уточнение: renderer передаёт только содержимое (или данные для формирования), но не путь. Запись файла — в main после подтверждения диалога. На будущей мобиле этот метод PlatformApi заменится на «сохранить файл + share sheet» — интерфейс должен это допускать, например возвращая результат «сохранено/отменено» без предположений о диалоге ОС.)
Уведомления — только через слой платформы (см. раздел 5). Текст уведомления — из валидированных полей блока, без HTML. Планировщик не должен читать/писать ничего вне файла БД; reminderFiredAt пишется тем же атомарным путём, что и остальная БД.

## 7. Сборка и CI

GitHub Actions: workflow build.yml с матрицей по ОС (windows-latest, macos-latest, ubuntu-latest).
(Уточнение: matrix job: checkout → setup-node (фиксированная версия) → npm ci → npm test → npm run build → electron-builder на соответствующем раннере → upload-artifact с именованным артефактом платформы (app-win.zip, app-mac.zip/dmg, app-linux AppImage). Каждая ОС пакуется на родном раннере — Wine и прочие костыли не нужны. Workflow запускается на push в main и вручную (workflow_dispatch). Кэш npm — опционально.)
Локальная полная сборка не обязательна: основной путь артефактов — CI; локально достаточно dev, test и typecheck.
(Уточнение: если локальная сборка под чужую ОС требует экзотики (иконки, ресурсы) — не усложняй, доводи формат до рабочего в CI.)
Мобильных job (Android/Xcode) в этом ТЗ нет — см. раздел 9.

## 8. Этапы

M0. Каркас. Репозиторий, .gitignore, Electron+Vite+React+TS, пустое окно, настроенная безопасность из раздела 6, интерфейс PlatformApi с electron-реализацией и browser-заглушкой, скрипты dev, build, test.
Готово, если: npm run dev открывает окно и работает на ОС разработки; renderer поднимается в обычном браузере через browser-адаптер; npm run build проходит; npm test запускается (пусть и без тестов) и завершается успешно; в окне нет ошибок в консоли, связанных с безопасностью; git status чистый после сборки (артефакты в .gitignore).
M1. Данные. Типы, чтение/запись JSON (атомарная), бэкап, миграции, валидация, тесты. Реализации хранилища — за интерфейсом (electron-файл, browser-память/localStorage).
Готово, если: тесты проходят, повреждённый файл не убивает приложение.
(Уточнение: проверь сценарии: файла нет; файл пустой; файл с невалидным JSON; файл с валидным JSON, но неверной схемой; файл с schemaVersion новее известной. Во всех случаях приложение стартует и не теряет данные безвозвратно (бэкап или чистая БД с понятным сообщением).)
M2. Календарь. Недельный/дневной/месячный вид, создание, перетаскивание, ресайз, диалог, удаление, проекты с цветами.
Готово, если: все операции сохраняются и переживают перезапуск на всех поддерживаемых ОС (минимум — на ОС разработки).
(Уточнение: проверь создание блока мышью, перетаскивание между днями, ресайз, редактирование через диалог, удаление; после каждого действия — перезапуск и проверка, что состояние на месте. Проверь, что архивированный проект не предлагается при создании, но отображается в истории.)
M2.5. Планирование на будущее. Навигация по будущим неделям/месяцам, создание запланированных блоков (planned: true), визуальное отличие, корректное поведение при переходе «будущее → настоящее».
Готово, если: блок, созданный на следующей неделе/месяце, сохраняется, переживает перезапуск, отображается отличным стилем, и отчёт по умолчанию его не суммирует (или суммирует отдельно — согласно решению в DECISIONS.md).
M3. Таймер и трей. Start/Stop, восстановление запущенного таймера, трей (десктоп), горячие клавиши (десктоп, Cmd на macOS).
Готово, если: таймер, запущенный перед закрытием, продолжается после старта; закрытие окна сворачивает в трей.
(Уточнение: также проверь, что «Выход» из трея завершает приложение; что Space не срабатывает в поле ввода; что Ctrl/Cmd+N и Ctrl/Cmd+E работают; что после Stop создаётся ровно один Entry с корректными start/end. Логика таймера не должна зависеть от трея и горячих клавиш — на мобиле их не будет.)
M3.5. Напоминания. Поле reminder в диалоге, планировщик в слое платформы, системные уведомления через сервис уведомлений, reminderFiredAt, глобальный выключатель, пересчёт при изменении времени блока.
Готово, если: напоминание срабатывает в назначенное время при запущенном приложении (в том числе свёрнутом в трей); повторно не показывается; при переносе блока срабатывает по новому времени; при выключенных уведомлениях не показывается; после перезапуска запланированные напоминания не теряются.
M4. Отчёт и экспорт. Сумма по проектам за период, CSV (UTF-8 с BOM, разделитель `;`, чтобы Excel открывал нормально), диалог сохранения через слой платформы.
Готово, если: суммы совпадают с ручным подсчётом на тестовых данных.
(Уточнение: подготовь набор тестовых данных с блоками на границах периода и с блоками без проекта; сверь суммы вручную. Проверь, что CSV открывается в Excel с русскими символами и корректными колонками; что разделитель именно `;`, что файл в UTF-8 с BOM.)
M5. Сборка и документация. build.yml с матрицей, артефакты под три ОС, README с инструкцией.
Готово, если: артефакты собираются в Actions под каждой ОС; в README описано, как запускать и где лежат данные.
(Уточнение: README содержит: требования по ОС, как запустить собранный артефакт под каждой ОС, где лежит файл данных (конкретные пути userData для Windows/macOS/Linux), как сделать бэкап, известные ограничения (напоминания работают только при запущенном приложении). Артефакты скачиваются из Actions и запускаются на чистых машинах.)
(Уточнение к порядку: M2.5 логично делать сразу после M2, M3.5 — после M3, до M4. Если удобнее иначе — зафиксируй в DECISIONS.md и не смешивай этапы в одном коммите.)

## 11. Приёмка (общая)

npm run build и npm test проходят на чистом клоне (CI-матрица по трём ОС зелёная).
npm audit — без critical/high (или с обоснованием в отчёте).
Нет сетевых запросов в рантайме (проверить DevTools → Network).
Данные переживают перезапуск и повреждение файла.
В репозитории нет секретов и .env.
Запланированные блоки на будущие недели/месяцы создаются, сохраняются и переживают перезапуск.
