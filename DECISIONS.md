## 2026-11-21 · M0 · Оркестрация dev/build для Electron+Vite
- Варианты: (а) electron-vite; (б) вручную: vite + tsc для main/preload + concurrently + wait-on.
- Выбрано: (а) electron-vite 6.0.0.
- Причина: один хорошо поддерживаемый пакет вместо трёх (concurrently, wait-on, cross-env) плюс
  готовая корректная сборка main/preload/renderer и dev-режим с запуском Electron. Меньше кода и
  зависимостей — требование ТЗ «минимум зависимостей». Альтернатива «своими руками» — больше
  кода и типовых ошибок (CJS/ESM preload, внешние зависимости main).

## 2026-11-21 · M0 · Версии пакетов
- Зафиксированы точные версии без `^`/`~` (ТЗ §0). Стек: electron 45.4.1, electron-vite 6.0.0,
  vite 8.3.8, @vitejs/plugin-react 6.3.0, react/react-dom 19.3.1, typescript 7.0.2 (tsgo),
  vitest 5.1.1. Все peerDependencies совместимы (проверены по реестру npm).
- electron postinstall скачивает бинарник — разрешён ТЗ явно («postinstall только для известных
  пакетов (electron, esbuild)»).
- electron-builder намеренно НЕ установлен: он нужен только на M5 (минимум зависимостей на этап).

## 2026-11-21 · M0 · CSP в dev-режиме
- Вопрос: строгий `script-src 'self'` ломает dev: @vitejs/plugin-react инжектит inline-прелюд
  Fast Refresh, а meta-CSP нельзя ослабить HTTP-заголовком (политики пересекаются).
- Варианты: (а) ослаблять CSP только в dev плагином transformIndexHtml; (б) 'unsafe-inline'
  всегда; (в) отключить Fast Refresh.
- Выбрано: (а). В dev к script-src добавляется 'unsafe-inline'; prod-бандл выходит строгим
  (проверяется грепом out/renderer/index.html). 'unsafe-inline' для style-src оставлен всегда —
  его требует оверлей ошибок React, пример директив в ТЗ это допускает.

## 2026-11-21 · M0 · Каталог данных в разработке
- По ТЗ §0: в dev данные лежат в каталоге проекта — выбран `.data/` (в .gitignore);
  в собранном приложении — `app.getPath('userData')`. Путь определяется в storage.ts по

## 2026-11-21 · M0 · Глобальный store UI
- На M0 общего UI-состояния нет (локальный state компонента-заглушки). Единый store вводится на
  M2 вместе с календарём; выбор между Zustand и reducer фиксируется тогда же (ТЗ §5 допускает
  оба). Не считаем это долгом: store — обёртка над одним источником истины, добавляется за один
  коммит.

## 2026-11-21 · M0 · Browser-режим dev
- `npm run dev:browser` — обычный vite с тонким vite.browser.config.ts (тот же корень
  src/renderer, те же плагины). Альтернатива — запуск renderer из electron.vite.config, но
  electron-vite всегда поднимает и Electron. Отдельный конфиг — 12 строк без дублирования
  логики приложения.

## 2026-11-21 · M0 · frame-ancestors в CSP
- Вопрос: пример директив в ТЗ содержит `frame-ancestors 'none'`, но в `<meta>` Chromium
  игнорирует эту директиву и печатает ошибку в консоль — против критерия M0 «нет ошибок,
  связанных с безопасностью».
- Варианты: (а) оставить в meta с фоновым шумом; (б) убрать из meta, при необходимости задать
  HTTP-заголовком (в этом приложении окно грузится локально и iframe-встраивание исключено
  архитектурно — заголовок не нужен вовсе).
- Выбрано: (б). frame-ancestors убрана из meta-CSP; фрейм-защита обеспечивается отсутствием
  удалённого контента и webview.

## 2026-11-21 · M0 · Конфиги vite/vitest как .mts
- Vite 8 анонсировал native-загрузчик конфигов (ESM-синтаксис в .ts, загружаемом как CJS, даёт
  предупреждение). vite.browser.config и vitest.config переименованы в .mts; electron.vite.config.ts
  загружает сам electron-vite — предупреждений нет.

## 2026-11-21 · M1 · Поведение при повреждении файла
- Вопрос: что делать, когда основной файл битый.
- Варианты: (а) старт с чистой БД и сообщением; (б) авто-восстановление из бэкапа;
  (в) спрашивать пользователя диалогом.
- Выбрано: (б) с деградацией в (а). Если бэкап читается — откатываемся к нему,
  основной файл сразу перезаписывается восстановленным (иначе каждое окно «восстанавливалось»
  бы заново), битая копия сохраняется в db.corrupt.json. Бэкап нетронут. Если бэкапа нет или
  он тоже бит — чистый старт с явным сообщением, битый файл тоже сохранён в db.corrupt.json.
  Диалог (в) — лишний UI-код без выгоды: пользователь всё равно не чинит JSON руками.
- too-new (схема новее): файл не перезаписывается вообще (флаг на каталог в fileStore),
  запись отключена, приложение стартует с сообщением.

## 2026-11-21 · M1 · Механизм миграций
- Реализован runner с явной цепочкой шагов {from,to,migrate} (src/shared/migrations.ts),
  боевая цепочка пуста: текущая версия 1, поля планирования в v1 опциональны и читаются
  со значениями по умолчанию — повышать версию ради них не за чем (ТЗ §3). Цепочка и целевая
  версия параметризуются, тесты гоняют синтетическую 1→2 без фейковых версий в проде.
  Нет шага для текущей версии → данные считаются повреждёнными с причиной (не «прочитаем
  как-нибудь»).

## 2026-11-21 · M1 · Разделение storage на fileStore + обёртку
- Логика файла (атомарная запись, бэкап, восстановление, tmp-чистка) вынесена в
  fileStore.ts: только node:fs/node:path, без electron. Electron-привязка (выбор каталога) —
  в storage.ts. Причина: сценарии M1 тестируются на реальной ФС в node-окружении без
  запуска Electron; путь userData остаётся единственным electron-местом.

## 2026-11-21 · M2 · FullCalendar: линейка v6
- Вопрос: версии. В реестре есть v7 (7.1.5) — новая мейор-линейка с переписанной архитектурой
  (peer temporal-polyfill, @full-ui/headless-calendar) и иным набором плагинов.
- Варианты: (а) v6.1.22 (react/daygrid/timegrid/interaction — ровно состав ТЗ §2);
  (б) v7 (несовместим с составом ТЗ, зрелость ниже).
- Выбрано: (а), весь комплект 6.1.22 единой версией (peer core ~6.1.22 совпадает).

  Русская локаль — из @fullcalendar/core/locales/ru (тот же пакет, отдельной зависимости нет).

## 2026-11-21 · M2 · font-src 'self' data:
- Иконочный шрифт FullCalendar встроен в бандл как base64 data: URL и блокировался
  font-src 'self' (ошибка в консоли против критерия приёмки). data: — ресурс локальный
  (ни сети, ни CDN), добавлен в font-src. Альтернатива «выкинуть иконки» ломает тулбар FC.

## 2026-11-21 · M2 · Единый store UI
- Варианты (ТЗ §5 «Zustand или reducer»): (а) zustand 5.1.0; (б) useReducer + Context.
- Выбрано: (а). «Один store» требуется явно; на Context+reducer пришлось бы писать очередь
  сохранений и селекторы поверх. Zustand ~3 КБ, без транзитивных зависимостей, активная
  поддержка; селекторы-функции дают точечные подписки без дополнительного кода.
  Производные значения (суммы, архив/активныe) — чистые функции-селекторы, в state не дублируются.
- Стратегия записи: оптимистичное обновление store, последовательная очередь saveDb;
  при ошибке — баннер и ресинхронизация состояния из хранилища (оно авторитетно).
  Компенсационные откаты по одной мутации не делаем: приложение однопользовательское,
  локальный файл, очередь исключает взаимную перезапись.

## 2026-11-21 · M2 · Мелкие выбора UI (разрешены ТЗ «реши и зафиксируй»)
- Drag и resize сохраняются немедленно; при отказе валидации view FC откатывается (revert).
- Удаление блока — из диалога одним нажатием, без подтверждения (утрата одного блока
  недороги, диалог уже «тяжёлый»). Отмена диалога блок не создаёт.
- Шаг сетки и минимум выделения — 15 минут (slotDuration 00:15, snapRangeUtc в shared
  с тестами); выравнивание по UTC-границам шага.
- Вид и дата в сессии не сохраняются между перезапусками (всегда текущая неделя):
  simplest, без состояния в схеме; если захотим — добавится полем в settings (schemaVersion 2).
- В шапке — суммарное время за сегодня через totalsForRange: витрина расчёта сумм для M4,
  отдельного долга не создаёт.
