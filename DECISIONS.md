## 2026-11-21 · M0 · Оркестрация dev/build для Electron+Vite
- Варианты: (а) electron-vite; (б) вручную: vite + tsc для main/preload + concurrently + wait-on.
- Выбрано: (а) electron-vite 6.0.0.
- Причина: один хорошо поддерживаемый пакет вместо трёх (concurrently, wait-on, cross-env) плюс
  готовая корректная сборка main/preload/renderer и dev-режим с запуском Electron. Меньше кода и
  зависимостей — требование ТЗ «минимум зависимостей». Альтернатива «своими руками» — больше
  кода и типовых ошибок (CJS/ESM preload, внешние зависимости main).

## 2026-11-21 · M0 · CSP в dev-режиме
- Вопрос: строгий `script-src 'self'` ломает dev: @vitejs/plugin-react инжектит inline-прелюд
  Fast Refresh, а meta-CSP нельзя ослабить HTTP-заголовком (политики пересекаются).
- Варианты: (а) ослаблять CSP только в dev плагином transformIndexHtml; (б) 'unsafe-inline'
  всегда; (в) отключить Fast Refresh.
- Выбрано: (а). В dev к script-src добавляется 'unsafe-inline'; prod-бандл выходит строгим
  (проверяется грепом out/renderer/index.html). 'unsafe-inline' для style-src оставлен всегда —
  его требует оверлей ошибок React, пример директив в ТЗ это допускает.

## 2026-11-21 · M0 · Browser-режим dev
- `npm run dev:browser` — обычный vite с тонким vite.browser.config.ts (тот же корень
  src/renderer, те же плагины). Альтернатива — запуск renderer из electron.vite.config, но
  electron-vite всегда поднимает и Electron. Отдельный конфиг — 12 строк без дублирования
  логики приложения.

## 2026-11-21 · M0 · frame-ancestors в CSP
- Вопрос: пример директив в ТЗ содержит `frame-ancestors 'none'`, но в `<meta>` Chromium
  игнорирует эту директиву и печатает ошибку в консоль — против критерия M0 «нет ошибок,
  связанных с безопасностью».
- Варианты: (а) оставить в meta с фоновым шумом; (б) убрать из meta, при необходимости задать
  HTTP-заголовком (в этом приложении окно грузится локально и iframe-встраивание исключено
  архитектурно — заголовок не нужен вовсе).
- Выбрано: (б). frame-ancestors убрана из meta-CSP; фрейм-защита обеспечивается отсутствием
  удалённого контента и webview.

## 2026-11-21 · M0 · Конфиги vite/vitest как .mts
- Vite 8 анонсировал native-загрузчик конфигов (ESM-синтаксис в .ts, загружаемом как CJS, даёт
  предупреждение). vite.browser.config и vitest.config переименованы в .mts; electron.vite.config.ts
  загружает сам electron-vite — предупреждений нет.

## 2026-11-21 · M1 · Поведение при повреждении файла
- Вопрос: что делать, когда основной файл битый.
- Варианты: (а) старт с чистой БД и сообщением; (б) авто-восстановление из бэкапа;
  (в) спрашивать пользователя диалогом.
- Выбрано: (б) с деградацией в (а). Если бэкап читается — откатываемся к нему,
  основной файл сразу перезаписывается восстановленным (иначе каждое окно «восстанавливалось»
  бы заново), битая копия сохраняется в db.corrupt.json. Бэкап нетронут. Если бэкапа нет или
  он тоже бит — чистый старт с явным сообщением, битый файл тоже сохранён в db.corrupt.json.
  Диалог (в) — лишний UI-код без выгоды: пользователь всё равно не чинит JSON руками.
- too-new (схема новее): файл не перезаписывается вообще (флаг на каталог в fileStore),
  запись отключена, приложение стартует с сообщением.

## 2026-11-21 · M1 · Механизм миграций
- Реализован runner с явной цепочкой шагов {from,to,migrate} (src/shared/migrations.ts),
  боевая цепочка пуста: текущая версия 1, поля планирования в v1 опциональны и читаются
  со значениями по умолчанию — повышать версию ради них не за чем (ТЗ §3). Цепочка и целевая

  Нет шага для текущей версии → данные считаются повреждёнными с причиной (не «прочитаем
  как-нибудь»).

## 2026-11-21 · M1 · Разделение storage на fileStore + обёртку
- Логика файла (атомарная запись, бэкап, восстановление, tmp-чистка) вынесена в
  fileStore.ts: только node:fs/node:path, без electron. Electron-привязка (выбор каталога) —
  в storage.ts. Причина: сценарии M1 тестируются на реальной ФС в node-окружении без
  запуска Electron; путь userData остаётся единственным electron-местом.

## 2026-11-21 · M2.5 · Планирование: флаг vs время
- Вопрос: что есть «запланированность» — флаг planned в файле или сравнение с now.
- Выбрано: флаг фиксирует намерение (создание/перенос в будущее — store ставит planned сам,
  перенос в прошлое — снимает); отображение и расчёты смотрят на время (isPlanned = флаг И
  start > now). При наступлении start флаг в файле НЕ сбрасывается автоматически (ТЗ §3),
  но блок перестаёт быть «плановым» в UI и в индикаторе.
- Суммы: убрал проверку флага из totalsForRange — входит всё с end <= now (фактическая трата);
  будущее отсекается самим условием. Незавершённый блок (end > now) не входит целиком —
  правило ТЗ «end <= now» буквально; досчитывать прошедшую часть незавершённого не стали.
- Отдельную колонку планов в отчёт (разрешено ТЗ) не завёл: индикатор «план недели»
  (кол-во + минуты, plannedMinutesForRange с отсечкой по границам недели) в шапке.
- Переход «будущее → настоящее» без перезапуска: now живёт в store и тикает каждые 30 с.
- Выбор даты: input[type=date] над календарём, gotoDate на локальный ПОЛДЕНЬ выбранного дня
  (дата воспринимается как день; полдень не сдвигает сутки на границах поясов).
- Границы прошлое/будущее (start == now, end == now, касание периода) закреплены
  детерминированными тестами с явным now (planning/sums/week .test.ts); сквозная проверка —
  smoke шаги 3/4 (план +7 дней: не виден на этой неделе, виден с planned-стилем на следующей).

## 2026-11-21 · M2 · Единый store UI
- Варианты (ТЗ §5 «Zustand или reducer»): (а) zustand 5.1.0; (б) useReducer + Context.
- Выбрано: (а). «Один store» требуется явно; на Context+reducer пришлось бы писать очередь
  сохранений и селекторы поверх. Zustand ~3 КБ, без транзитивных зависимостей, активная
  поддержка; селекторы-функции дают точечные подписки без дополнительного кода.
  Производные значения (суммы, архив/активныe) — чистые функции-селекторы, в state не дублируются.
- Стратегия записи: оптимистичное обновление store, последовательная очередь saveDb;
  при ошибке — баннер и ресинхронизация состояния из хранилища (оно авторитетно).
  Компенсационные откаты по одной мутации не делаем: приложение однопользовательское,
  локальный файл, очередь исключает взаимную перезапись.

## 2026-11-21 · M2 · Мелкие выбора UI (разрешены ТЗ «реши и зафиксируй»)
- Drag и resize сохраняются немедленно; при отказе валидации view FC откатывается (revert).
- Удаление блока — из диалога одним нажатием, без подтверждения (утрата одного блока
  недороги, диалог уже «тяжёлый»). Отмена диалога блок не создаёт.
- Шаг сетки и минимум выделения — 15 минут (slotDuration 00:15, snapRangeUtc в shared
  с тестами); выравнивание по UTC-границам шага.
- Вид и дата в сессии не сохраняются между перезапусками (всегда текущая неделя):
  simplest, без состояния в схеме; если захотим — добавится полем в settings (schemaVersion 2).
- В шапке — суммарное время за сегодня через totalsForRange: витрина расчёта сумм для M4,
  отдельного долга не создаёт.

## 2026-11-21 · M3.5 · Напоминания: где планировщик и как гасятся дубли
- Планировщик — в main (ТЗ §4): setTimeout на ближайший срок + пересчёт на каждом
  db:load/db:save. Смена системного времени — watchdog polling 15 с (событий ОС о смене
  часов нет; дешёвый пересчёт дешевле дрейфа). Офлайна без приложения нет: напоминания
  живут, пока процесс запущен (в т.ч. в трее) — зафиксировано в KNOWN_ISSUES.
- Владелец reminderFiredAt — UI-store (единый писатель файла): main шлёт
  'reminder:fired', store помечает идемпотентно (уже помеченный блок не перезаписывается).
  PlatformApi.remindersSetEnabled не заводил: выключатель — settings.notificationsEnabled
  в том же файле, канал один (saveDb), отдельный метод продублировал бы состояние.
- Просрочка: старше N=60 минут — не показываем, но помечаем cleanup-ом (ТЗ «например, 60»,
  фиксирую 60). Граница now == due — созревает; now - due == cutoff — ещё показываем.
- Дубли: основной страж — reminderFiredAt в файле; на окно между показом и записью
  отметки — shownOnce в памяти main (watchdog не покажет второй раз, пока save в полёте).
  Перенос блока: resetReminderOnTimeChange (shared, тесты) снимает отметку — сработает по
  новому времени; перенастройка reminder в диалоге — тоже снимает.
- Browser-режим: системные уведомления — оговорённое ТЗ §5 исключение, адаптер no-op'ит
  onReminderFired; планировщика в браузере нет.

## 2026-11-21 · M3 · Таймер: владение и правила
- Владение: таймер — поле DbFile.timer (таймстарт), единый писатель — UI-store.
  Трей НЕ владеет таймером: меню шлёт команду 'toggle' в renderer
  (PlatformApi.onTimerCommand), а label пункта синхронизирует UI
  (PlatformApi.setTimerActive). На платформах без трея оба метода no-op —
  логика таймера от трея/хоткеев не зависит (ТЗ §4 M3).
- Повторный Start при активном таймере — ИГНОРИРУЕТСЯ (не замена): случайный
  двойной клик не теряет уже идущий отрезок времени; замена молча обнулила бы
  начало часового трекинга.
- Stop сразу после Start (или при отставших системных часах): валидатор требует
  end > start, поэтому блок короче шага сетки удлиняется до 15 минут
  (timerStopRange в shared, тесты). «Приложение было закрыто» — частный случай:
  старт — таймстарт в файле, блок всегда один от startedAt до Stop.
- Растущий блок обновляется раз в секунду: общий now в store тикает 1000 мс
  (ТЗ разрешает «раз в N — зафиксируй»; отдельный тикер для таймера не заводил —
  плановые стили и суммы тоже пересчитываются чаще, цена — лишний рендер в секунду).
- Виртуальный блок таймера в календаре: id '@timer', не кликабелен, не двигается.

## 2026-11-21 · M3 · Горячие клавиши — keydown в renderer, не menu/globalShortcut
- Варианты: (а) accelerator в приложенном меню; (б) globalShortcut; (в) keydown-слушатель.
- globalShortcut перехватывал бы Space/комбо всей системе — перебор; menu-accelerator
  не даёт правила «не в поле ввода» (менеджер меню не видит фокус input).
- Выбрано (в): слушатель keydown в App под флагом hasHotkeys. Cmd/Ctrl+N — диалог нового

  скролла; Cmd/Ctrl+E — перехватывается, показывает баннер-задел до M4 (экспорт — этап M4,
  в M3 не смешиваем). В browser-режиме hotkeys выключены флагом — по ТЗ «только десктоп».

## 2026-11-21 · M4 · Отчёт и CSV
- Разделители: BOM + `;` + CRLF — Excel RU/Pages открывают без настройки кодировки
  (приёмка проверяет вручную; automated-тест фиксирует байты EF BB BF и отсутствие запятой
  как разделителя). Экранирование: `"` удваивается, ячейка с `"`/`;`/переносом — в кавычки.
- Отчёт = тот же totalsForRange, что и сайдбар: сумма считается в одном месте, цифра в окне
  и в CSV не может разойтись. Период «включительно» (конец = полночь следующих суток),
  границы режут блоки отсечкой. Архивные проекты остаются в отчёте по их блокам.
- Даты периода конвертируются через локальную зону (isoToLocalInput), иначе на границах
  UTC-дней выбранный диапазон съезжал бы на день.
- Ctrl+E открывает отчёт; файл пишет кнопка «Экспорт CSV» — клавиша не должна внезапно
  открывать системный диалог. Плановые блоки в отчёт не входят (не потраченное), это
  сказано в подсказке модалки и комментарии CSV.
- В smoke диалог сохранения заменён env TZ_SMOKE_EXPORT_PATH: приёмка проверяет настоящий
  файл (BOM/разделитель/экранирование кавычек/ИТОГО/CRLF) без модального окна.
